## 1. 한 문장 정의

> **여러 기관에 흩어진 시험의 원서접수·시험·발표 일정을 한곳에서 검색·비교하고, 필요한 순간 공식 사이트로 바로 이동하게 하는 웹서비스.**

로그인 없이 아래 네 질문에 답하는 것이 전부다.

1. 찾는 시험이 있는가?
2. 지금 접수할 수 있는가?
3. 접수와 시험이 언제인가?
4. 어디에서 공식 정보를 확인하거나 접수하는가?

### 1.1 원래 정의와 뒤집은 사유

원래 정의는 이랬다.

> ~~내가 준비하는 시험 여러 개의 원서접수·시험·발표 일정을 하나의 가로 타임라인에 올려, 일정이 겹치는 구간을 미리 찾아주는 웹서비스.~~
>
> ~~이 서비스가 파는 것은 **여러 시험을 동시에 준비할 때 생기는 충돌의 발견**이다.~~

두 가지가 실측으로 무너졌다.

**① 겹침은 정보가 아니었다.** 시험 이벤트의 98%가 기간 시행이라 기간끼리는 거의 항상 겹친다. 실제로 충돌 117건이 떴고 그중 106건이 "접수 기간이 겹쳐요" 였는데, 접수는 겹쳐도 순서대로 하면 되므로 사용자가 할 일이 없다. 겹침 자체를 파는 순간 대부분이 소음이 된다.

**② 충돌을 보려면 먼저 시험을 골라야 했다.** 그 앞단이 진입 장벽이다. 검색으로 들어온 사람이 알고 싶은 것은 "지금 접수할 수 있는가" 하나인데, 그 답을 보려면 종목 선택과 응시일 지정을 먼저 통과해야 했다.

그래서 **선택 없이도 전체 일정을 보여주고, 공식 기관 연결을 종착점으로 삼는** 정보 허브로 바꿨다. 겹침은 판정하지 않고 기간을 나란히 보여주기만 한다 — 기간 시행이면 그 안에서 날짜를 고르면 되고, 그 판단은 사용자의 것이다.

## 2. 문제 정의

### 2.1 관찰된 문제

취업 준비 중인 청년은 보통 자격증 2~4개와 어학 시험 1~2개를 병행한다. 그런데 각 시험의 일정은 서로 다른 기관의 서로 다른 사이트에 흩어져 있다.

| 시험 | 확인해야 하는 곳 |
|---|---|
| 정보처리기사, 산업안전기사 등 | q-net.or.kr |
| 컴퓨터활용능력, 워드프로세서 | license.korcham.net |
| TOEIC, TOEIC Speaking | exam.toeic.co.kr |
| 한국사능력검정 | historyexam.go.kr |
| KBS한국어능력 | kbskorean.org |
| 빅데이터분석기사 | dataq.or.kr |

그 결과 세 가지 실패가 반복된다.

1. **접수 마감을 놓친다.** 회차가 연 3~4회뿐인 시험은 한 번 놓치면 3~4개월이 밀린다.
2. **일정 충돌을 뒤늦게 발견한다.** A시험 실기 접수 기간과 B시험 시험일이 같은 주에 걸린 걸 시험 2주 전에 알게 된다.
3. **역산을 못 한다.** "지금 시작하면 몇 회차를 노려야 하나"를 계산하려면 접수·시험·발표 6개 날짜를 손으로 늘어놓아야 한다.

### 2.2 기존 대안과 그 한계

| 대안 | 한계 |
|---|---|
| Q-Net 공식 사이트·앱 | 공단 시행 종목만. 타 기관 시험과 나란히 못 봄 |
| 블로그·카페 정리글 | 갱신이 안 되고, 작성자가 고른 몇 종목만 |
| 개인 캘린더 수기 입력 | 6개 날짜 × 시험 개수를 손으로 입력. 변경 반영 안 됨 |
| 월간 캘린더 형태의 일정 사이트 | **원서접수는 기간이고 시험일은 하루**인데 격자가 이 둘을 같은 칸에 뭉갬. 충돌이 안 보임 |

마지막 항목이 원래 가로 타임라인을 택한 이유였다.

**그 진단은 맞았지만 처방이 틀렸다.** "격자가 기간과 시점을 같은 칸에 뭉갠다" 는 관찰은 정확하다. 다만 그것은 격자의 한계가 아니라 **하루 한 칸에 점만 찍는 구현**의 한계였다. 주 단위 그리드에 레인을 배정하면 기간 막대가 주 경계를 넘어 이어지고, 접수는 테두리·시험은 채움·발표는 점선으로 갈라진다. 뭉개지지 않는다.

타임라인을 버린 결정적 이유는 따로 있다. 가로 타임라인은 **여러 시험을 이미 고른 사람**에게만 뜻이 있는데, 실제 유입은 시험 하나를 검색해서 들어온다. 사람들이 자기 일정을 기억하는 단위도 월이다.

## 3. 타깃

### 3.1 1차 타깃

**자격증·어학 시험을 2개 이상 동시에 준비하는 20대 취업 준비생.**

시험을 하나만 준비하는 사람은 해당 기관 사이트만 봐도 충분하다. 이 서비스의 가치는 **동시 준비 개수에 비례**한다. 따라서 타깃을 "취업 준비생 전체"로 넓히지 않고 "복수 준비자"로 좁힌다.

### 3.2 대표 시나리오

> 25세, 전기 계열 전공. 하반기 공채를 목표로 전기기사(필기 합격, 실기 대기)와 산업안전기사를 함께 준비 중이고, 토익 점수도 만들어야 한다. 세 시험의 접수·시험 날짜를 한 화면에 올려놓고 "10월에 뭐가 몰려 있나"를 확인하고 싶다.

### 3.3 명시적 비(非)타깃

- 공무원 수험생 — 시험이 사실상 1개이고 일정이 널리 알려져 있어 이 서비스의 이점이 없다
- 이미 특정 시험 하나만 준비하는 사람
- 시험 정보(합격률, 공부법)를 찾는 사람 — 이 서비스는 **일정만** 다룬다

## 4. 차별점

| # | 차별점 | 경쟁 대안이 못 하는 이유 |
|---|---|---|
| 1 | **기관을 넘나드는 한 화면** | 각 기관 사이트는 자기 종목만 보여줄 이유가 있음 |
| 2 | **구간과 시점의 시각적 구분** | 월간 격자로는 표현 불가. 타임라인이어야 함 |
| 3 | **충돌 자동 탐지** | 사람이 6개 날짜 × N개 시험을 눈으로 비교하는 일을 대신함 |
| 4 | **회원가입 없이 즉시, 링크 공유 가능** | 로그인 벽이 있는 서비스는 첫 방문 이탈이 큼 |

3번이 이 서비스의 방어선이다. 단순 집계는 누구나 복제할 수 있지만, "겹치는 구간을 판정한다"는 계산이 들어가면 제품이 된다.

## 5. MVP 범위

### 5.1 포함

| 영역 | 내용 |
|---|---|
| 플랫폼 | 웹 (모바일 웹 우선, 반응형) |
| 콘텐츠 | **시험 일정만.** 58종목 큐레이션 |
| 인증 | **소셜 로그인만, 그리고 선택 기능.** 구글·카카오. 로그인 없이 전 조회 기능 사용 가능 |
| 수집 개인정보 | **소셜 제공자 ID와 닉네임뿐.** 이메일·이름·전화번호 받지 않음 |
| 상태 유지 | URL 쿼리스트링 + `localStorage`. 로그인 시 조합 저장 |
| 내보내기 | **`.ics` 파일 다운로드** |
| 공식사이트 연결 | 전 종목. `jmCd` 기반 Q-Net 딥링크 자동 생성 |
| 핵심 화면 | 종목 선택 → 타임라인 → (종목 단독 페이지) |
| 백엔드 | **일정 조회는 정적 파일만.** 회원 기능만 Cloudflare Workers + D1 |
| 수요 검증 | 익명 집계 (선택 종목 수, 저장·내보내기 실행률) |

### 5.2 제외 (의도적)

| 제외 항목 | 이유 |
|---|---|
| 알림 발송 | MVP는 "수요가 있나"를 검증. 알림은 검증 후 |
| 이메일 수집 | 알림이 없으니 이메일을 쓸 데가 없다. 받지 않으면 카카오 비즈 앱 전환도 불필요 |
| 자체 이메일·비밀번호 가입 | "단순하다"는 직관과 반대로 부담이 가장 크다. 비밀번호 일방향 암호화 법적 의무, 재설정에 메일 발송 불가피, Workers CPU 10ms에서 bcrypt 부적합 |
| 이메일 매직링크 로그인 | 메일함을 열어야 하는 마찰 |
| 네이버 로그인 | 사전 검수 영업일 2~4일. 검수 전에는 테스터 20명까지만 로그인 가능 |
| 캘린더 구독(ICS URL) | Google 캘린더 구독은 갱신이 24~48시간이고 PC 웹에서만 추가 가능하며 개별 삭제 불가. `.ics` 파일 다운로드로 대체 |
| 청년 정책·지원금 | 데이터 성격이 다름(신청기간 비정형). Phase 3 |
| 모바일 앱 | Play 신규 개인 계정은 테스터 12명 × 14일 연속 옵트인 필요. MVP 속도를 해침 |
| 시험 정보(합격률, 교재) | 범위 확산. 일정에만 집중 |

**로그인을 다시 넣은 이유**: 초안에서는 무회원을 원칙으로 삼았는데, "저장해두고 다시 보고 싶다"는 요구는 URL 공유로 완전히 해결되지 않는다. 다만 **로그인은 선택 기능이고 조회에는 벽이 없다.** 구글은 non-sensitive 스코프만 쓰면 OAuth 검증이 불필요하고, 카카오는 회원번호·닉네임이 기본 제공이라 심사가 없다. 둘 다 절차 대기 없이 붙일 수 있어서 MVP 속도를 해치지 않는다.

### 5.3 MVP의 검증 질문

알림도 회원 기능도 없으니 리텐션은 측정 대상이 아니다. MVP가 답해야 하는 질문은 셋뿐이다.

1. **이 정보를 찾는 사람이 있나** → 검색 유입량, 종목 단독 페이지 유입
2. **복수 선택이 실제로 일어나나** → 선택 종목 수 분포. 중위값이 1이면 가설이 틀린 것
3. **다시 보러 올 의사가 있나** → 조합 저장 전환율, `.ics` 내보내기 실행률

2번이 가장 중요하다. 선택 종목 수의 중위값이 1이라면 "복수 준비자" 타깃 가정이 무너지고, 제품 방향을 다시 잡아야 한다.

## 6. 데이터 전략

### 6.1 수집 등급

| 등급 | 정의 | 종목 수 |
|---|---|---|
| T1 | Q-Net 시험일정 API 직결 | 47 |
| T2 | 종목코드는 있으나 시행기관이 공단 아님. 응답 유무 **실측 필요** | 6 |
| T3 | Q-Net 밖. 개별 크롤링 | 4 |
| T4 | 상시시행. 규칙 카드로만 표현 | 1 |

상세는 `docs/데이터-스키마.md`, 종목 목록은 `data/exams.seed.json`.

### 6.2 확정된 제약

- **Q-Net 시험일정 API 응답에 종목 식별자가 없다.** 요청 시 넣은 `jmCd`로만 귀속 가능 → 종목별 루프 불가피. `jmCd`를 가진 53종목(T1 47 + T2 6) × 1회 = 53호출/일, 개발계정 1,000건/일로 충분
- **실시간 호출은 하지 않는다.** 시험 일정은 연초 확정 후 거의 불변 → 하루 1회 배치로 정적 JSON 생성. DB·서버 불필요
- **컴퓨터활용능력은 상시시험**이라 타임라인 막대로 표현할 수 없다. "접수는 시험일 4일 전까지" 규칙 카드로 처리

### 6.3 최우선 실측 과제

키 발급 직후 `jmCd = 0492`(컴활 1급), `1324`(빅데이터분석기사), `1325`(정보보안기사)를 테스트한다. 응답이 나오면 T2 6종목이 T1로 승격되어 크롤러 개발이 줄고, 안 나오면 해당 종목을 규칙 카드 또는 외부 링크로 강등해야 한다. **이 결과가 개발 범위를 좌우한다.**

### 6.4 저장 매체

**일정 데이터는 정적 JSON, 회원 데이터만 DB(Cloudflare D1).** 실측 결과 1년치 216회차가 brotli 압축 후 **9.7KB**, 3년 누적도 27KB에 불과해 DB 도입이 정당화되지 않는다. 상세 검증은 `docs/04-저장-전략-검증.md`.

Supabase 무료 티어는 **7일 저활동 시 자동 일시정지**되고 복구가 수동이라 배제했다. 알림 기능이 붙은 뒤 "일주일 조용했더니 DB가 멈춰서 마감 알림이 안 갔다"가 실제로 가능한 시나리오다.

### 6.5 공식사이트 연결

Q-Net 종목 상세 페이지는 **타 기관 시행 종목(컴활·빅데이터분석기사·정보보안기사)까지 포함**하므로 `jmCd` 하나로 53종목 전부를 단일 URL 패턴으로 커버할 수 있다.

단 잘못된 `jmCd`는 오류 없이 **엉뚱한 종목을 정상 응답으로 표시**한다(`9999`=인수통합종목, `2010`=폐지 종목, 미지정=백지). 사용자를 잘못된 시험 정보로 보내는 것은 마감을 놓치게 만드는 것과 같은 종류의 피해이므로 화이트리스트 검증이 필수다.

### Phase 2 — 알림

MVP의 이메일 전환율이 유의미할 때 착수. 채널 선택지는 셋이고, 각각 전제가 다르다.

| 채널 | 전제 | 비용 |
|---|---|---|
| 카카오 알림톡 | **개인사업자 등록 필수**(홈택스 무료·당일). 템플릿 심사는 화이트리스트 방식 | 13원/건 |
| 모바일 앱 푸시 (FCM/APNs) | Play 테스터 12명 × 14일, Apple $99/년 | 무료 |
| 이메일·웹푸시 | 없음 | 무료 |

이메일·웹푸시는 도달률이 낮다. Google 공식 발표로 **알림 상호작용률이 1% 미만**이고, 2025년 10월부터 크롬이 미상호작용 사이트의 알림 권한을 자동 회수한다.

알림톡을 택하는 경우, 심사·비용·사용자 경험이 모두 같은 제약을 가리킨다 — **명시적으로 관심 등록한 항목만, 개수 상한을 두고 발송.** 미신청자 대상 "마감 임박" 홍보는 심사에서 반려된다.

### Phase 3 — 청년 정책·지원금

시험 일정과 데이터 성격이 다르다.

- **캘린더화 가능**: 온통청년 청년정책 API(3,981건), K-Startup 공고, 기업마당 — 신청기간이 정형
- **캘린더화 불가**: 정부24·보조금24·복지로 — 신청기간이 `"전년도 4~5월"` 같은 자유 텍스트이거나 필드 자체가 없음

여기서 시험 일정에는 없는 두 기능이 나온다.

- **자격 개시 D-day** — 거주 요건("해당 지역 N개월 이상")을 아직 못 채운 사용자에게 *자격이 생기는 날*을 미래 이벤트로 제시
- **청년 자격 소멸 카운트다운** — 정책별 연령 상한(만 34·39·45세, 지역별 상이)이 달라서, 생일이 지나면 특정 정책군에서 영구 탈락. 남은 기간과 사라질 정책 목록 표시

두 기능 모두 어떤 기존 서비스도 하지 않는다. 다만 **거주 요건·연령 상한을 정형 데이터로 파싱하는 것**이 기술적 심장이 되므로, MVP 단계에서 착수하지 않는다.

### Phase 4 — 모바일 앱

Phase 2에서 알림 수요가 확인되고 웹 트래픽이 쌓인 뒤. 확인된 제약은 아래와 같고, 특히 두 번째가 제품 설계에 직접 영향을 준다.

- Play 신규 개인 계정: 테스터 12명 × **14일 연속** 옵트인 → 프로덕션 심사 7일
- **삼성 기기는 16일 미사용 시 deep sleeping** 상태가 되어 알림을 수신하지 못한다(3일 미사용 시 sleeping). 마감 알림 앱은 원래 열 이유가 없어서 이 상태에 쉽게 빠진다 → 앱을 주기적으로 열 이유(자격 카운트다운 등)가 **기술적 필수품**이 된다
- Play 정책상 `USE_EXACT_ALARM`은 알람·타이머·캘린더 앱만 허용. 마감 알림은 해당 없음 → 부정확 알람으로 충분하도록 설계
- 마감일은 사전 확정값이므로 **로컬 예약 알림**이 1차 수단. 서버 푸시는 신규·변경 브로드캐스트에만

## 8. 성공 지표

### MVP (3개월)

| 지표 | 목표 | 의미 |
|---|---|---|
| 선택 종목 수 중위값 | **2개 이상** | 타깃 가정 검증. 가장 중요 |
| 종목 단독 페이지 검색 유입 | 월 1,000 세션 | SEO가 유일한 성장 엔진 |
| 타임라인 도달률 | 방문 대비 40% | 종목 선택 UI가 작동하는지 |
| 조합 저장 전환율 | 타임라인 도달 대비 5% | 재방문 의사. Phase 2 착수 근거 |
| `.ics` 내보내기 실행률 | 타임라인 도달 대비 10% | 알림 대신 캘린더로 해결하려는 수요 |
| 공유 링크 유입 | 전체 유입의 10% | 무회원 조회 전략의 바이럴 효과 |

### 판단 기준

- 선택 종목 수 중위값이 1 → **타깃 재정의.** 타임라인의 존재 이유가 사라짐
- 검색 유입이 안 붙음 → SEO 구조 점검. 회원 기능을 붙여도 해결되지 않음
- 저장 전환율 5% 미달 → Phase 2 알림 착수를 보류하고 콘텐츠 확장을 먼저 검토
- **`.ics` 내보내기가 저장보다 훨씬 많이 쓰이면** → 사용자는 우리 서비스에 머물 생각이 없고 캘린더로 가져가려는 것. 알림보다 캘린더 연동 품질을 높이는 게 우선순위

| 리스크 | 영향 | 대응 |
|---|---|---|

| 크롤링 대상 사이트 구조 변경 | T3 4종목 일정 누락 | 소스별 부분 실패 허용. 실패 시 이전 빌드 유지 + "최종 확인: N일 전" 표시 |
| 대한상의 robots.txt 제약 | 컴활 정기시험 일정 자동수집 불가(`/kor/` 경로 금지) | 자동수집 시도하지 않음. 상시시험 규칙 안내로 대체 |
| 재방문 유인 부재 | 일회성 조회 도구로 끝남 | 조합 저장과 `.ics` 내보내기로 최소한의 재방문·재사용 경로 확보. 다만 알림이 없는 한 리텐션은 여전히 검증 대상이 아님 |
| 잘못된 `jmCd`로 오정보 링크 | 사용자를 다른 시험 페이지로 보냄 | 화이트리스트 검증 + 미검증 시 목록 페이지 폴백 (FR-LNK-03) |
| 회원 기능이 MVP 속도를 잠식 | 출시 지연 | 소셜 로그인 2개만, 저장 목록 CRUD만. 프로필·설정 화면 없음. 조회 동선은 백엔드에 의존하지 않게 분리 |
| 탈퇴 시 데이터 미파기 | 개인정보보호법 제21조 위반 | 영구 삭제로 구현. `deleted_at` 플래그 금지를 요구사항으로 고정 (NFR-PRIV-05) |
| Q-Net 운영계정 심의 미승인 | 개발계정 1,000건/일에 묶임 | 50호출/일이므로 개발계정으로 충분. 활용사례 등록으로 증액 신청 |
| 범위 확산 | 정책·알림·앱을 MVP에 끌어들여 출시 지연 | 5.2 제외 목록을 변경 이력과 함께 유지 |

## 10. 용어

| 용어 | 정의 |
|---|---|
| 종목 | 하나의 시험 자격 (예: 정보처리기사) |
| 회차 | 한 종목의 한 시행 단위 (예: 2026년 정기 기사 3회) |
| 이벤트 | 회차에 속한 날짜 하나. 접수·시험·발표 |
| 구간 이벤트 | 시작일과 종료일이 다른 이벤트. 타임라인에서 막대 |
| 시점 이벤트 | 시작일과 종료일이 같은 이벤트. 타임라인에서 점 |
| 상시시험 | 확정 일정 없이 규칙만 있는 시험 (컴활, OPIc) |
| 충돌 | 선택된 두 종목의 이벤트가 같은 주에 걸치는 상태 |
| jmCd | Q-Net 종목코드 4자리 |
