# 저장 전략 검증 — 정적 JSON vs DB

문서 버전 0.1.0 · 2026-08-13 · 상태: **결론 확정**

---

## 0. 결론

> **일정 데이터는 정적 JSON, 회원 데이터만 DB(Cloudflare D1).**
> 읽기 전용 데이터와 쓰기 데이터를 같은 저장소에 두지 않는다.

| 데이터 | 저장소 | 근거 |
|---|---|---|
| 시험 일정 (읽기 전용) | **정적 JSON + CDN** | 1년치 전량이 brotli 압축 후 **9.7KB**. DB를 쓸 이유가 없음 |
| 종목 마스터 (읽기 전용) | **정적 JSON** | 2.5KB |
| 원본 API 응답 스냅샷 | **저장소 커밋 (아카이브)** | 매핑 버그 사후 복구용 |
| 회원 계정 · 저장 목록 (쓰기) | **Cloudflare D1** | 유휴 정지 정책 없음. 무료 유지 |
| 세션 | **D1 테이블** (KV 아님) | KV 무료 티어는 쓰기 1,000건/일 |

---

## 1. 검증한 질문

"API에만 의존하는 것보다 조회 후 DB 저장이 낫지 않나"라는 문제 제기를 세 개로 분해했다.

| # | 질문 | 답 |
|---|---|---|
| 1 | 런타임에 Q-Net API를 직접 호출해야 하나 | **아니다.** 이미 배제한 설계였고 그 판단이 맞다 |
| 2 | 조회 결과를 저장한다면 매체가 파일이어야 하나 DB여야 하나 | **파일.** 실측 크기가 DB를 정당화하지 못한다 |
| 3 | DB가 필요해지는 시점은 언제인가 | **쓰기가 생길 때.** 즉 회원 기능이 들어오는 지금이다 |

**중요한 정리**: 현재 설계의 정적 JSON은 이미 "조회 후 저장"이다. 하루 1회 API를 조회해 파일로 굳히고, 사용자 요청은 그 파일만 읽는다. 논점은 "저장하느냐"가 아니라 "**무엇에 저장하느냐**"였다.

## 2. 런타임 API 직접 호출을 배제하는 근거

| 문제 | 내용 |
|---|---|
| 호출량 | 응답에 종목 식별자가 없어 **종목별 루프가 불가피**하다. 사용자 1명이 3종목을 선택하면 3회 호출. 개발계정 1,000건/일이면 하루 **약 333명**에서 고갈 |
| 응답 시간 | 3종목 선택 시 외부 API 3회 왕복이 첫 렌더 경로에 들어간다. NFR-PERF-01(2초) 달성 불가 |
| 가용성 | Q-Net API 장애 = 사이트 장애. 우리가 통제할 수 없는 단일 장애점 |
| 키 노출 | 클라이언트에서 직접 호출하면 `serviceKey`가 노출된다. 프록시를 두면 서버가 필요해진다 |
| 데이터 성격 | 시험 일정은 연초 확정 후 거의 불변이다. 초 단위 신선도가 아무 가치를 만들지 않는다 |

마지막 항목이 결정적이다. **실시간성이 가치를 만들지 않는 데이터에 실시간 호출을 쓰면 비용만 남는다.**

## 3. 실측 — 정적 JSON 크기

상시시험 제외 54종목에 대해 스키마(`docs/데이터-스키마.md` §3) 형태의 데이터를 생성해 측정했다. 회차당 이벤트 6개, `source` 메타 포함.

| 데이터 범위 | 원본 | gzip | brotli |
|---|---|---|---|
| 1개 연도 · 종목당 3회차 (162회차) | 171.3 KB | 10.3 KB | **7.6 KB** |
| 1개 연도 · 종목당 4회차 (216회차) | 228.4 KB | 13.4 KB | **9.7 KB** |
| 1개 연도 · 종목당 6회차 (324회차) | 342.6 KB | 19.4 KB | **14.0 KB** |
| 2개 연도 누적 (432회차) | 456.8 KB | 27.7 KB | **18.5 KB** |
| 3개 연도 누적 (648회차) | 685.2 KB | 43.4 KB | **27.2 KB** |
| 종목 마스터 58개 | 13.1 KB | 3.0 KB | **2.5 KB** |
| 키 축약 + `source` 제거 (216회차) | 58.4 KB | 2.5 KB | **1.8 KB** |

### 해석

- **현실적인 최대치(3년 누적, 648회차)가 brotli 27KB**다. 웹폰트 한 개보다 작다
- 압축률이 20배 이상 나오는 이유는 날짜 문자열과 라벨의 반복성이 극단적으로 높기 때문이다. `"필기 원서접수"`가 수백 번 반복되는 데이터다
- 압축 후 크기를 실제로 지배하는 것은 **`source.hash`(64자 hex)**다. 무작위 문자열이라 압축이 안 된다. 클라이언트 페이로드에서 `source`를 제거하면 216회차가 1.8KB까지 줄어든다
- 참고 기준: 모바일 웹 페이지 총 무게 중위값이 약 2,362KB(HTTP Archive 2025-07)다. 27KB는 그 **1.1%**다

### 판단

**이 크기에서 DB 도입은 정당화되지 않는다.** DB를 넣으면 얻는 것 없이 다음을 잃는다.

- 무료 티어 유휴 정지 리스크
- 배포 단위의 원자성 (파일은 커밋 하나가 데이터 스냅샷 하나)
- 롤백 단순성 (`git revert`)
- CDN 엣지 캐시

**단, 클라이언트 페이로드에서 `source`를 분리한다.** 해시와 수집 메타는 빌드 파이프라인 내부 정보이므로 별도 파일에 두고 브라우저로 보내지 않는다.

## 4. 검토한 DB 대안

| 서비스 | 판정 | 결정적 사유 |
|---|---|---|
| **Cloudflare D1** | **채택** (회원 데이터용) | 유휴 정지 정책 없음. 읽은 행 5M/일, 쓴 행 100k/일, DB 500MB. egress 무과금 |
| Neon Free | 차선 | 0.5GB, 100 CU-h/월. 5분 유휴 시 scale-to-zero이나 **쿼리 시 자동 복귀**라 실질 무해. Postgres가 꼭 필요하면 이것 |
| **Supabase Free** | **배제** | **7일 저활동 시 프로젝트 자동 일시정지**. 복구는 대시보드 수동 클릭. 트래픽 적은 개인 서비스에 치명적 |
| Turso Free | 배제 | **10일 미사용 시 아카이브** + 2025년 이후 방향 전환·팀 감축으로 플랫폼 리스크 |
| SQLite 파일을 Git 커밋 | 부분 채택 | 읽기 전용 시드에는 가능. **쓰기 저장소로는 부적합**(동시성·원자성 없음). 회원 이메일을 공개 저장소에 커밋할 수 없음 |

**Supabase 배제가 이 검증의 실질적 성과다.** 무료 티어 비교에서 가장 흔히 추천되지만, 7일 미접속 자동 정지는 초기 트래픽이 없는 서비스에 정면으로 불리하다. 알림 기능이 붙은 뒤 "일주일 조용했더니 DB가 멈춰서 마감 알림이 안 갔다"가 실제로 가능한 시나리오다.

## 5. 회원 기능이 들어올 때의 구조

MVP에서 회원가입을 도입하기로 결정했으므로(`docs/02-요구사항-정의서.md` FR-ACC) 쓰기 저장소가 필요해진다. **읽기와 쓰기를 분리한다.**

```
정적 호스팅 (CDN)
├─ /                        S-01 종목 선택
├─ /timeline                S-02 타임라인
├─ /exam/{slug}             S-03 종목 페이지 (58개 사전 생성)
└─ /data/*.json             일정 데이터 (읽기 전용, 장기 캐시)

Cloudflare Workers (경량 API)
├─ /api/auth/*              소셜 로그인 콜백, 세션
├─ /api/lists               저장한 시험 목록 CRUD
└─ /api/account             탈퇴 · 데이터 삭제
        │
        └─ Cloudflare D1
           ├─ users         (provider, provider_user_id) UNIQUE
           ├─ sessions
           └─ saved_exams
```

**일정 데이터는 여전히 Workers를 거치지 않는다.** 로그인하지 않은 사용자는 정적 파일만 받으므로 MVP의 핵심 동선이 백엔드에 의존하지 않는다. Workers가 죽어도 타임라인은 동작한다.

### D1 사용 시 주의점

| 항목 | 내용 |
|---|---|
| 인터랙티브 트랜잭션 없음 | `BEGIN…COMMIT` 불가. `db.batch([...])`로 원자성 확보 |
| 인덱스 쓰기 계상 | 신규 회원 1명 = 2 rows written(테이블 + 인덱스). 100k/일이면 하루 5만 로그인 여유 |
| 읽기 복제 | 켜면 "write-then-read"가 깨질 수 있다. **MVP에서는 켜지 않는다** |
| Worker 호출당 쿼리 50개 | D1 쿼리도 subrequest에 계상. OAuth 콜백 1회가 약 5회 소모 |
| Workers Free CPU 10ms | 네트워크 대기는 계상되지 않지만, Cloudflare 자신이 "인증 처리는 통상 10~20ms"라고 명시. 콜백 핸들러를 얇게 유지 |

세션을 KV가 아니라 D1에 두는 이유가 두 개다. KV 무료 티어의 **쓰기 한도가 1,000건/일**이고, KV는 변경 전파가 **최대 60초 이상** 걸려 로그아웃이 즉시 반영되지 않는다.

## 6. 원본 응답 아카이브 (추가 결정)

**정적 JSON과 별개로, Q-Net API 원본 응답을 날짜별로 저장소에 남긴다.**

이유는 두 가지다.

1. **매핑 버그의 사후 복구.** `docRegStartDt` 계열 10개 필드를 이벤트 배열로 정규화하는 과정에 버그가 있었다면, 원본이 없으면 과거 데이터를 재구성할 수 없다
2. **과거 연도 조회 가능 여부가 미확인이다.** `implYy=2024`로 과거 데이터를 계속 준다는 보장이 문서에 없다. 지금 받은 것을 남겨두지 않으면 영구히 잃는다

원본 응답은 정규화 결과보다 크지만, 압축 후 회차당 수백 바이트 수준이므로 연간 수십 KB에 불과하다. 저장소에 두기에 충분히 작다.

## 7. 변경 감지와 이력

Phase 2 알림에서 "일정이 변경되었습니다"를 보내려면 이전 상태와 비교가 필요하다. 이것이 DB를 요구하지는 않는다.

- 회차별 `source.hash`를 정적 JSON에 유지 → 이전 빌드와 비교
- 변경분은 빌드 로그 + 별도 `changes.json`으로 누적
- **git 히스토리 자체가 이력 저장소다.** 특정 날짜의 일정 상태를 알고 싶으면 해당 커밋을 보면 된다

DB가 실제로 필요해지는 것은 **"누구에게 무엇을 언제 보냈는가"**를 기록할 때다. 그건 알림 기능이 실제로 붙는 Phase 2의 문제이고, 그때도 D1로 충분하다.

## 8. 요구사항 반영

| 요구사항 | 변경 |
|---|---|
| NFR-OPS-01 | "백엔드 서버·DB 없이 운영" → **"일정 데이터 제공 경로는 백엔드 없이 운영"**으로 축소. 회원 기능은 Workers + D1 사용 |
| NFR-OPS-02 | 월 운영비 0원 유지 — Workers·D1 무료 티어 내 |
| NFR-PERF-03 | 초기 페이로드 200KB 이하 → 실측 근거로 **50KB 이하**로 강화 |
| 신규 | `source`를 클라이언트 페이로드에서 분리 |
| 신규 | 원본 응답 아카이브 |

## 9. 미확인

| 항목 | 확인 방법 |
|---|---|
| Q-Net API가 과거 연도(`implYy=2024`)를 응답하는지 | 키 발급 후 실호출 |
| 실제 회차 수 (종목당 연 몇 회인지) | 실호출. 위 추정은 3~6회 가정 |
| D1 cold start 지연 | 공식 문서에 언급 없음. 실측 필요 |
| Supabase "충분한 활동"의 정량 임계값 | 공식 미공개 |
